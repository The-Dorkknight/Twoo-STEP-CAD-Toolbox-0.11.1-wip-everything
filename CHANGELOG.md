(`## 0.11.4-wip — edge-keeping smoothing for scans, a better "is it a scan?" test, a question before a scan is converted, two bugs the benchmarks found

- **One folder for your files: `Files/`** (was `Output/`, with the upload hidden in `runtime/work`). A dropped STL is saved into its own project folder, `Files/<name>/`, and the STEP and the `.log.txt` land beside it (a chained job, or a file you put in a project folder yourself, uses that folder too). Dropping a file that is already there, byte for byte, reuses it (no second copy). The scratch folder now holds only temporary job files. `TOSTEP_OUTPUT` still overrides the folder.

- **Every job's whole log is saved** as `<result name>.log.txt` beside the STEP file (found missing when the real S99 run's console had only the last lines). Best effort: a read-only folder never fails a conversion.
Reported (19 November 2026): the real S99 scan converted in 15 minutes but as 6 flat faces, 5 round faces, 472 freeform patches and 610 facet regions (worst point 2.09 mm). Then: *"assuming everything is a scan and straightening already straight triangles could cause trouble: run the ghost and box benchmarks, apply what is useful, and perhaps ask with a dialog."* Research note: `docs/research/SCAN_EDGES.md`.
- **Why a scan came out as hundreds of patches:** noise tilts neighbouring small triangles by about 10°, 11 % of the edges looked sharper than the crease angle, and the patch layout cut the surface at each (1,514 freeform patches of about 15 triangles on the stand-in).
- **New: edge-keeping smoothing** (`edgesmooth.py`, bilateral normal filtering): triangles are averaged only with neighbours that already point nearly the same way, so edges stay. Stand-in scan: neighbouring triangles 9.8° → 1.1° apart, mean distance to the true shape 0.013 → 0.007 mm, 2.4 s. Points on real edges and corners are pinned (a clean box's corners had moved 2.4 tolerances; now 0.10). `TOSTEP_EDGESMOOTH=0` turns it off.
- **Changed: "is it a scan?" is a better test.** 0.11.3 asked how far three smoothing passes moved the points and called two clean organic meshes scans. Now: over 100,000 triangles and neighbouring triangles tilted 2° or more at random (13° on every scan stand-in, 0.00 to 0.09° on every clean mesh tried: box, cylinder, ghost, rounded box, organic), or the clean-up had to act.
- **New: the question.** Before a file over 4 MB is converted the page asks the server if it looks like a scan, and if so asks: *Yes, treat it as a scan* / *No, it's CAD: use Classic* / Cancel. *Advanced → Is it a 3D scan?* and `--scan-mode auto|scan|cad` set it for good. Clean CAD and small files are never asked.
- **Changed: only scans are reduced and smoothed.** The 0.11.3 plain pre-reduction ran on every dense mesh and turned a clean 786,000-triangle box from 6 faces (0.11.1) into 11. A scan whose route is lathe or prismatic gets the smoothing and a scan route (guesstimate on, no histogram crease, no second reduction); any other scan is converted as in 0.11.3 (a bent organic stand-in took 307 s on 0.11.3, over 18 minutes and no result with the smoothing; with this rule 339 s).
- **Fixed: a CAD crash from 0.11.2, found by the golden gate.** The scan clean-up threw away every piece under 20 triangles as a "speck", so a small multi-body CAD part (two boxes of 12 triangles) lost everything and failed with `IndexError`. A piece is a speck only if tiny in area, or a handful of triangles *and* under 2 % of the biggest; if nothing is kept the biggest stays.
- **Changed: the prepared mesh is kept for the second engine** (the Standard preset looks with Quad patches, then hands over to Ladder; both loaded and prepared the same file).
- **Measured on the soldering-iron stand-in (Standard, Moderate):** 0.11.3 23.5 min, 78,547 faces, every curved area facets; this build 6 to 16 min across variants, 7,099 to 28,082 faces, 5 % of the area as facets in the best. **One of four runs hung** for over 37 minutes in the first "which faces cannot be drawn" mesh of the whole shape (found with py-spy); 0.11.3 has the same call. Not fixed (next step in SCAN_EDGES.md section 7).
- **Not run on the real S99 file with this build.**
- Tests: `tests/test_scan_edges.py` (15), all 240 pass; golden gate clean.

## 0.11.3-wip — a closed scan is a scan too, a sign of life with the stage and the clock, power settings, fewer round trips to the graphics card
Reported (19 November 2026): the S99 scan, 620,944 triangles, was *still very slow* on Turbo: 40 % processor at first, then after 30 minutes 15 %, and the last log line 21 minutes old. This build's version number was still 0.11.1-wip although it already held the 18 November scan changes, so nothing on screen said which build was running: **from now on the version number changes with every build** (this one is 0.11.3-wip; the 18 November scan work below shipped under the old 0.11.1-wip label).
- **Why the scan changes did nothing for it:** they started only when the *scan clean-up* had to act (loose pieces, holes). The real scan is one closed piece, so the clean-up did nothing, and with it went the light denoise and the pre-reduction. The guesstimate reduction then worked on all 620,000 triangles (351 s on the author's laptop, in the screenshot), and the noise was fitted as it was.
- **Changed: a dense mesh is a scan.** Any mesh over 150,000 triangles gets 3 light Taubin passes (kept only if there is noise to remove: the median point moves 0.054 mm on the test scan, 0.0000 mm on a clean dense mesh, so a clean one is left exactly as it was) and a plain quadric reduction to 150,000 triangles (3.4 s; kept only if the surface moved by no more than half the tolerance, else tried at twice the count). A reduction that comes out with stray non-manifold edges is now repaired (cut, then holes closed) instead of being thrown away. *Scan clean-up: off* skips all of it. On the closed test scan (648,638 triangles, Quick, 2 cores) the guesstimate reduction took 17 s instead of 351 s on the full mesh, and patch layout finished at 98 s where before it was still going after 5 minutes.
- **New: a sign of life that says where it is.** Every step of a conversion is named. While the log is quiet the page's progress line now reads "now: building faces and sewing them into a solid (4:12 in this step) · CPU 3.9 of 4.1 GHz". The worker writes a small status file and the app's server reads it, because while OpenCASCADE is working (writing and reading back a STEP of 60,000 facets, sewing) it holds Python's interpreter lock and nothing inside the worker can print. A "still ..." line is also written to the log when it can, and at the end *Where the time went* lists the steps that took 5 % or more.
- **New: the power check.** At the start of a conversion the log says if the computer is on battery, in a power-saving mode, has turbo boost off or the processor capped. About a minute in, the page checks again with the processor busy and says if its clock is below 45 % of its top speed. Linux (cpufreq, intel_pstate, power-profiles-daemon), Windows (power plan) and macOS (Low Power Mode) are read; nothing is changed. Guide: [docs/guide/performance.md](docs/guide/performance.md#power-settings).
- **Found by measuring, and the reason for 15 % processor:** the long silent stretch is not fitting. On the closed test scan (Quick, 2 cores, 15.9 minutes in all) **68 % of the run, 10 min 46 s, was the write-and-read-back repair loop** after the faces are built: up to 6 rounds, each merging faces, writing the whole STEP (about 10,000 faces, 427 areas as facets), reading it back, meshing the whole shape and testing every round face, then making the 1 to 3 faces it found into facets. It is one OpenCascade thread, so on an 8-thread laptop one busy thread is 12 to 15 %, whatever profile is chosen: Turbo cannot help a step that cannot use more than one core.
- **Tried and reverted: a time cap on those rounds.** With the rounds limited to 15 % of the time budget the run stopped them at 6:45 as intended, then hung for over 6 minutes in the final deviation measurement, inside OpenCascade's mesher, on a face it cannot draw: the very kind of face the rounds exist to catch. A faster run that can hang or write a file other CAD programs cannot draw is worse than a slow one, so the rounds are unchanged; a comment in the code says why.
- **Not fixed:** each write-and-read-back round is as slow as before (the next step: find the faces that cannot be drawn with a cheaper test before the first full round, so fewer rounds are needed), and a scan still comes out partly as facets when noise defeats the fit (denoise inside face groups, paper D25). Both are in `docs/research/SLOW_SCAN_2.md`. Tests: `tests/test_power_and_dense.py` (17).

## Before 0.11.3-wip (not versioned at the time) — fewer round trips to the graphics card
Reported: on an M5 MacBook with the card on, the Halloween cat (Fine preset) ran about twice as fast, "not as fast as expected".
- **Why only 2x:** the card scores only the v2 fitter's shape guesses. The rest of a conversion (building faces, sewing, STEP writing, the first pass of Fine) is OpenCascade, which is processor-only, so the whole job cannot speed up by more than the share the scoring has. In Fine on an Extreme profile the first pass and v2 also run side by side, so the job takes as long as the slower of the two.
- **Changed (all graphics cards, Apple Metal, Nvidia CUDA alike):** each block of guesses used to upload the whole triangle sample again and wait for the card before the next block. The sample is now uploaded once per round, blocks are queued, and the answer is read back once (`accel.score_blocks(sync=False)` + `accel.gather`). Blocks are 1024 guesses instead of 256. Same maths: the 37 GPU tests pass and a whole v2 conversion (PyTorch on the processor) gives the same faces and deviation as NumPy.
- **Not measured on a real card.** The saving is in fixed costs (uploads, waiting), so it should help most on small rounds; the size of it on the M5 is unknown. Press *Test it* and convert the cat again, then send the two times.
- **Low-end machines: the Potato profile reduces big meshes first.** Meshes over 30,000 triangles are reduced (outlines, flat faces and round features kept; the log says so) before converting. Measured on a 2-core Linux machine, 82,000-triangle organic test mesh, Quick engine: 107 s whole, 86 s reduced to 40,000, 45 s reduced to 20,000, 60 s with the Potato profile's 30,000; all closed, valid and inside tolerance. The price: a smooth part can come out as more, smaller faces (25 faces whole, 252 at 20,000 on the same mesh). Only Potato does this; Moderate and Extreme convert at full size. Switch profile, or untick *Protect memory*, to turn it off. `tests/test_potato_ceiling.py`.
- **Paper:** `docs/research/SOLID_EVIDENCE.md` / `.pdf` is now version 1.2: 23 figures and screenshots (before: none), new disclosures D16 (graphics-card scoring) and D17 (triangle ceiling), and updated research list, field report, honesty ledger and citation. D1–D15 are unchanged from version 1.1. `tools/build_paper_pdf.py` now embeds pictures.
- **New, experimental, off by default: the Coons gap filler** (*Advanced → Gap filler*, `--gap-fill`). Where the normal fit misses a freeform patch, a four-sided Coons patch is built on the patch's own outline (grown outwards along the mesh, then trimmed back by the shared outline), with its inside fitted to the mesh as in the Quad patches engine. Choices: plate filler (default, unchanged), Coons then plate, Coons only, none. Measured on the coarse blob and the ridged knob, each filler tried on every hard patch: within the tolerance on 14 of 29 patches against 6 for the plate filler, but about twice as slow per patch; whole parts came out about the same (blob 21 faces instead of 26 at 0.145 against 0.141 mm; knob unchanged; on a 64,950-triangle cat-like figure it was used on 1 of 57 patches and added 165 s). Tests: `tests/test_coons_fill.py`. Paper D18.
- **Per-region hybrid (quad patches plus exact faces): measured, not built.** On a blob cut flat at the bottom, neither quad remesher keeps an open boundary (QuadriFlow's edge ended 3.9 to 8.1 mm off the cut), and QuadriFlow's sharp-edge option left 24 of 56 rim quads crossing the rim (0.379 mm off, not closed). The method and the repair that would make it work are written up as paper D19.
- **Paper version 1.3:** D18 and D19, Figure 3 (the claim ladder) redrawn with what is built today (the old drawing said "not yet" for four-sided patches and Coons fill, though the Quad patches engine already made them), two new figures, the honesty ledger updated.
- **Paper version 1.5** (18 November 2026): D20 scan clean-up and the 3-hours-to-8-minutes measurements, D21 the faster patch layout (now described in full), D22 the background preview, D23 the SolidCraft link, and two ideas not built: D24 two triangles for a flat, D25 denoising inside face groups. Four new figures (29 in all, renumbered in reading order); the running joke in section 0 retired.
- **3D scans: much faster, and a clean-up step** (18 November 2026). A 620,924-triangle scan of a soldering iron took 3 h 6 min on Draft. On a stand-in scan with the same problems (653,119 triangles, noise, holes, 973 fragments, a turntable plate) Draft now takes **7.7 min** (closed, valid, 65 flat and 390 round faces, worst gap 0.085 mm) and Quick **8.4 min** (closed, valid, 0.052 mm, but all facets). Changes: *Scan clean-up* (new; Advanced, `--scan-cleanup`; automatic when the mesh isn't one closed piece) removes loose pieces, cuts non-manifold edges and fills holes; a dense scan gets 3 light denoise passes and a plain quadric pre-reduction to 150,000 triangles; a plain reduction stands in when the feature-keeping one can't stay closed (before, the run silently fell back to every triangle); Quick reduces meshes over 60,000 triangles; patch layout is 6x faster per step with identical results and logs a heartbeat every 20 s; the safety checkpoint is skipped above 60,000 triangles and under a 10-minute budget; the result preview is built in the background when a job finishes. Scans still come out largely faceted; a feature-aware denoise is the next step. Tests: `tests/test_scan_cleanup.py`. Note: `docs/research/SCAN_CLEANUP.md`.
- **Intel graphics: looked into, measured, not added.** A UHD 620 laptop said Intel graphics "need a different PyTorch build (XPU)". That was misleading: PyTorch's Intel build supports only Arc and Core Ultra graphics, and Intel says older UHD / Iris graphics will not be supported. The message now says so. And it would barely help: profiling the v2 fitter (the only part a card speeds up) on five test meshes put shape scoring at 0.2–9 % of the run (64,950-triangle cat-like figure: 1.1 s of 666 s), so even a perfect card saves a few percent. This also contradicts the 0.11.2 reading of the M5's 2x (scoring at least half the run); the GPU guide and paper (v1.4 note under D16) are corrected. Note: `docs/research/INTEL_GPU.md`.
- **New, experimental: SolidCraft link** (10 November 2026). SolidCraft (open-source Fusion-style CAD) has no plug-in runtime yet, so the toolbox talks to a running SolidCraft through its documented local control channel (token-protected, this computer only): *or take the selected mesh body from SolidCraft* under the Mesh drop area, *Send to SolidCraft* on every STEP result, and `tostep solidcraft` (all selected bodies, `--body`, `--file`, `--status`). Uses only `selection.get`, `file.export_stl` and `file.insert_step`; the mesh body is left alone. Tests: `tests/test_solidcraft.py`, against a stand-in that follows SolidCraft's protocol docs. **Not yet run against a real SolidCraft.** Guide: `docs/guide/solidcraft.md`; research note: `docs/research/SOLIDCRAFT.md`.
- **README and guides: more pictures.** The front page now shows the quality presets as the app draws them, the same three parts converted the normal way (Classic) and with roughing first (Staged), and the ghost test model with Guesstimate; the user guides show them where those features are described. All are the paper's own figures.
- **Tried and dropped:** a fast area for triangular faces instead of OpenCascade's integral. Exact (3e-9) but no faster once timed outside the profiler.

## 0.11.1-wip — graphics cards: seen is not the same as usable; renamed Twoo STEP CAD Toolbox
- **Renamed** (author's pun on to / two / too): *To STEP CAD Toolbox* → **Twoo STEP CAD Toolbox**, repository `twoo-step-cad-toolbox`, start files renamed to match. The package `tostep`, `TOSTEP_*` variables and CAD ids keep their names on purpose (D14).
Reported: the M5 MacBook showed nothing for graphics acceleration; a Ryzen 5 laptop with built-in Radeon graphics and a GTX 1060 showed the Nvidia card but it could not be selected.
- **Why the M5 showed nothing:** the graphics settings were inside the *Performance* card, which is hidden unless the *Advanced* preset is chosen. There is now an always-visible **Graphics card** box on the Convert tab.
- **Why the GTX 1060 could not be selected:** the tick-box stayed greyed out until a GPU pack was installed, and that pack was plain `pip install torch`. PyPI's current PyTorch has no code for Pascal (GTX 10-series) cards, so even an installed pack saw the card and failed on every operation. Now Pascal / Maxwell / Volta cards get the CUDA 12.6 build (`torch>=2.6,<2.15`, the last line that has it), and a real test, not the word "available", decides whether a card is ready.
- **New:** every card is listed with a tag (Ready / Needs support installed / Installed support does not work / Not usable) and a sentence saying why; one button installs or reinstalls the right build; **Test it** times the card against the processor; **Look again** re-reads the cards. The tick-box is never greyed out.
- **New command:** `tostep gpu` (list), `tostep gpu --install`, `tostep gpu --test`.
- **Safer:** a card that is seen but fails its test is ignored and the conversion runs on the processor, so a card problem cannot fail a conversion. Before this the v2 scoring would have thrown and fallen back mid-job.
- **Found on the first real test (an M5 MacBook):** the box said *Ready*, then *Test it* failed with "Cannot convert a MPS Tensor to float64 dtype as the MPS framework doesn't support float64". Apple's graphics backend has no float64 at all, and the scoring asked the card for a float64 answer. This bug is as old as the GPU pack: on a Mac the card path always threw and quietly fell back to the processor, so no Mac ever used its GPU. Fixed (inputs are converted before moving to the card; the answer is brought back to the processor before widening). *Ready* now requires the real scoring (planes, cylinders and spheres) to run on the card, not just matrix multiplication, which is why the box wrongly said Ready. **Not yet re-tested on the M5** — press *Test it* again; if another operation is missing on Metal, the box will now name it.
- **Honest limits:** the GPU speeds up only the v2 fitter's shape scoring (the *Fine* preset and *Second pass*), nothing else. AMD and Intel graphics are not used (PyTorch has no build this installer can set up for them). The route for GTX 10-series ends when PyTorch 2.14 is no longer installable. Not tested on any real card; see [docs/guide/gpu.md](docs/guide/gpu.md).
- **Tests:** `tests/test_gpu.py` (simulated GTX 1060 + Radeon laptop, M5, silent driver, endpoints, page placement; with PyTorch installed, the real maths against NumPy and the seen-but-cannot-run guard).

## 0.11.0-wip — a new name, a new shape, the same maths
First version of Twoo STEP CAD Toolbox, the long-term-support successor of STL2STEP / EVERYTHING to solid (last version 0.10.3-wip, now frozen).
- **One small core, tools as plug-ins.** Every tool (mesh → STEP, Jetwash, SCAD → STEP, Hardpoint STL, Image → STEP) is a folder with a `manifest.toml` and a `run(job)`; the web page, the command line and the CAD buttons are built from the manifests. Contract 1: [docs/PLUGIN_CONTRACT.md](docs/PLUGIN_CONTRACT.md). Adding a tool: [docs/ADDING_A_PLUGIN.md](docs/ADDING_A_PLUGIN.md).
- **Algorithms untouched.** Files were moved, imports rewritten mechanically. On the test knob the new layout writes a STEP with the same face count (69) and the same byte length (432,037) as 0.10.2.
- **One FreeCAD workbench and one Fusion add-in**, both thin: one shared bridge to the command line, one shared hardpoint reader, put together at install time. Renamed `TOSTEP`; new Fusion add-in id. Hand-written; **never run in the real programs** (LTS gate 4).
- **Golden benchmark** (`tools/golden.py`, `benchmarks/golden.json`): nine small generated parts with written limits; the release gate. It also locks in a known weakness: Classic leaves a 96-sided cylinder as 98 flat faces where Standard and Quick make 3.
- **Tests:** the 0.10.2 suite ported, plus 29 contract tests (manifests, registry, parameter rules, import layers, headers, page assembly, the CAD-command promise), 4 CAD-adapter tests and 3 headless-browser tests. Layers are enforced: plug-ins do not import front ends; a plug-in imports another only if it lists it in `requires`.
- **`pip install .`** works (console command `tostep`); the double-click start files remain the way for most people.
- **CI and release workflows written** (`.github/workflows`): tests + golden on Linux, macOS and Windows, versions recorded; release from `tostep/version.py`, newest four kept. **Not yet run on GitHub.**
- **Added:** `[io] preview` manifest flag (a plug-in whose result is not a mesh, so no 3D preview is offered); a clear error when a plug-in reports success without writing its result file; `TOSTEP_PLUGIN_PATH` for private plug-ins; a bad `--preset` is now a sentence, not a traceback.
- **Fixed on the way over:** Image → STEP's token-sheet error path crashed with a missing `import sys`.
- **Renamed:** environment variables `STL2STEP_*` → `TOSTEP_*`; CAD command ids `STL2STEP_*` → `TOSTEP_*`; start files; the `app/` folder is gone ([docs/MIGRATING_FROM_STL2STEP.md](docs/MIGRATING_FROM_STL2STEP.md)).
- **Removed:** the drop-in plug-in system (replaced by `TOSTEP_PLUGIN_PATH`, decision D4); the stand-alone apps.
- **Still true, said plainly:** nothing has run on a real Mac, Windows PC, FreeCAD or Fusion; dependencies are version ranges, not pins; Image → STEP is experimental; Quad patches were tried on five synthetic shapes. See [docs/KNOWN_LIMITATIONS.md](docs/KNOWN_LIMITATIONS.md) and the gates in [LTS_POLICY.md](LTS_POLICY.md).
